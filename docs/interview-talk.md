## 一、一句话定位（开场用）

「我用 LangGraph 把我自研的一套『按部就班不偏离』智能体工作流做成了可运行状态机：Agent 结合知识库检索、条件判断、大模型推理和工具调用去干活，每一步都不许跳、不许偏。它对应行业里**有状态的多步 Agent 编排（stateful multi-step agent orchestration）**。」

## 三、30 秒版（电梯陈述）

「我做过一套可控的多步 Agent 编排。核心是把工作流变成一张有状态图：先用知识库检索，命中才进推理，推理时判断是否要调工具，最后把结果沉淀进记忆。关键设计是**条件路由做护栏**——检索不到就不瞎编，而是追问用户补信息。这套东西在行业里就是 LangGraph 的标准用法，我当时是自己用 Node.js 零依赖实现的，后来用 LangGraph 复刻了一版做对照。」

## 四、3 分钟版（展开讲）

1. **痛点**：普通 Chain 是直线，跑完即焚，无法在中间做「判断要不要调工具」「检索不到怎么办」这类分支，Agent 容易跑偏。
2. **我的做法**：用图（Graph）代替链（Chain）。图有三要素——**节点**是每一步动作，**边**是流转条件，**状态**是全局黑板。所有节点读写同一块状态，这就是「不偏离」的锚。
3. **具体节点**：检索 → 判断 →（命中）推理 →（需工具）调工具 → 回收记忆；（未命中）直接追问。
4. **护栏价值**：`judge` 节点的条件边保证「检索为空绝不进入推理乱答」，这是交付级系统必备的可靠性设计，不是玩具 Demo。
5. **工程化对照**：我自研那套用 Node.js 零依赖网关（OpenAI 兼容，多模型池化）实现，LangGraph 版是工业标准框架的等价实现，两者架构同构。

## 五、高频追问 & 标准回答

**Q1：你真用过 LangGraph 还是只是跑了个 Demo？**
A：「两个都算。我自研系统本质就是这套编排思想，LangGraph 是把它标准化。这件作品是我把自研逻辑用工业框架复刻出来做面试弹药，代码是我让技术搭子实现的，架构和路由规则是我定的——这点我不包装。」

**Q2：为什么不用普通 Chain 而用 Graph？**
A：「Chain 是单向直线，没有中间状态判断。我的场景必须在『检索后』决定走推理还是追问、在『推理后』决定调不调工具，这是有状态的分支编排，Graph 天然适配，Chain 要硬塞 if-else 反而难维护。」

**Q3：检索为空就追问，会不会影响体验？**
A：「恰恰相反，这是可靠性设计。乱答比追问伤害更大——尤其在我这种业务系统里，答错一个运营动作可能影响 45 家门店的执行。护栏优先于流畅度。」

**Q4：你的 Memory 怎么做的？**
A：「Demo 里用 State 的 `memory` 字段把本轮 Q+A 沉淀，真实系统里我接的是 LLM×RAG 双轨——既做对话记忆召回，也做知识库检索，对应行业里的 Episodic Memory + RAG。」

## 六、你和 junior 应用开发的区别（护城河话术）

- **junior**：能写 `prompt | llm | parser`，但说不清「为什么要 Graph 而不是 Chain」「护栏怎么设计」。
- **你（架构视角）**：你定的是**编排结构、路由规则、护栏边界**，落地交给工具链。面试时你讲得出「为什么这么拆、每个节点的职责、偏离了会怎样」——这是交付负责人和纯码农的分水岭。

> 一句话：你卖的不是「我会写框架」，是「我能设计一套不偏离、可落地的 Agent 系统，并且有团队把它交付出来」。

## 七、事实 / 推测 边界

- **可验证事实**：LangGraph 的定位是「有状态的多步 Agent 编排框架」，条件边（`add_conditional_edges`）和共享状态（`State`）是其核心机制；本 Demo 已离线跑通两个分支（命中+调工具 / 未命中+追问），输出轨迹可复现。
- **个人推测（非事实）**：部分大厂面试官会追问「为什么不用 Chain」「护栏怎么保证」，本稿已覆盖；但若现场要求手写 Graph 代码，本作品不直接覆盖，需另开一条编码训练线（你之前已明确暂不做）。
